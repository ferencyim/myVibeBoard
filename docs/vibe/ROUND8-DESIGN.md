# 第八轮设计：#1 即群聊、方案多模型互审、任务间互相感知

> 2026-10-26。需求见 [PRODUCT-REQUIREMENTS.md](../../PRODUCT-REQUIREMENTS.md) 第八轮。建立在 [ROUND6-DESIGN.md](ROUND6-DESIGN.md) 的原生多 tab 之上：每个 tab 仍是独立原生会话，不恢复第五轮的群聊容器。

## 1. tab 与角色

| tab       | 角色          | 职责                                                                       |
| --------- | ------------- | -------------------------------------------------------------------------- |
| #1 主会话 | main（群主）  | 和用户对话、派活给各 tab、跟进与汇总；时间线里汇集各 tab 的进展            |
| #2 方案   | planner       | 按模型列表写方案：第 1 个模型写，其余依次审阅，第 1 个模型汇总修订出最终版 |
| #3 探路   | scout（共享） | 接受任一 tab 的调查请求，结论回给提问的 tab                                |
| #4 执行   | worker        | 执行已确认方案，管理子代理（任务看板）、后台命令与终端                     |
| #5 复核   | reviewer      | 代码复核                                                                   |
| #6 验证   | verifier      | 测试与证据，验证作废规则不变                                               |

- 原「方案复核」角色（plan_reviewer）并入 #2：#2 的模型设置从单个模型改为模型列表（至少 1 个）。旧设置迁移为「planner 模型 + plan_reviewer 模型（若启用）」。
- 编号在任务内固定。第八轮之前创建的任务保持原编号，只补缺的角色 tab，编号接着往后排。
- 新任务（含维护任务）默认建齐 #1–#6，建 tab 不发送提示词。角色在任务、项目、全局均未配置时，沿用任务主会话 tab 的 provider/model/thinking，权限仍按该角色规则，来源显示「沿用 #1 模型」。仅用户显式将探路、复核设为「不启用」才省略对应 tab。
- 回退贯穿方案模型列表、确认快照、执行准入、复核和验证；未配置方案模型列表时，仅以 #1 模型写作，不创建审阅者。流程面板、vibe_tabs 和主会话 roster 采用同一解析结果，不能将未配置误报为未启用。

## 2. #1 群聊

### 2.1 用户点名某个 tab

用户在 #1 输入以 `@#n` 开头的消息（composer 上也提供「发给」选择器），这条消息以用户身份直接送到 #n，#1 的模型不跑这一轮。#n 收到的就是用户消息，权威与用户在 #n 里直接说话相同（例如 `@#4 开始执行` 等同在 #4 里说，即执行授权）。#1 时间线留一条「已转给 #n」的状态行，#n 回合结束后它的结论再回到 #1。

宿主目前没有「用户消息送达 agent 之前」的插件钩子，只能在回合开始后补救，模型已经开跑。因此需要一个最小 [core]：

- 新增插件 before 钩子 `agent.user_prompt`。它只对用户消息触发，agent 互发的消息不经过。插件可以返回 `{ handled: true, note }`：宿主不把这条消息送给目标 agent，在其时间线追加一条用户消息记录和插件提供的说明。
- 插件处理掉的消息由插件以用户身份投给 #n。宿主插件 API 的 send 不带 sourceAgentId 即为用户来源；只有插件验证过这条消息来自用户在 #1 的输入时才这样做。

### 2.2 进展汇报

以下事件发生时，向 #1 追加状态行（插件 timeline item，不触发模型，不耗 token）：

- 每个 tab 回合结束：交接包里的结论摘要；
- 阶段变化；
- 某个 tab 在等审批：写明去 #n 处理；
- 子代理认领与完成；
- 失败。

需要模型判断时，#1 的 agent 自己用 `vibe_tabs` / `get_agent_activity` 去读。

### 2.3 群主职责

#1 的提示词写明：

- 理解用户意图后，需求交给 #2 出方案，调查交给 #3，执行由用户授权后交给 #4；
- 跟进各 tab 并在 #1 汇总；
- 自己不写方案、不改代码；
- 不能替用户确认方案或审批。

## 3. #2 方案多模型互审

1. 用户在 #1 提需求，#1 转给 #2；用户也可以直接在 #2 里说。
2. #2 的写作模型（列表第 1 个，就是 #2 tab 自己）出初稿，格式为 vibe-plan 加中文 Markdown 正文。
3. 审阅：#2 依次以子代理身份为列表中第 2 个起的每个模型开一个审阅者（不占顶部 tab），每个审阅者拿到初稿和前面所有审阅意见，做完整评估，输出意见。
4. 修订：#2 的写作模型汇总全部意见，出最终方案，并在方案末尾附「审阅意见处理」：采纳了哪些、没采纳哪些及理由。
5. 最终方案的摘要和链接汇报到 #1，等用户确认（`/执行`、面板「执行」、`@#4`，或直接在 #4 发消息）。
6. 审阅过程由插件编排：初稿完成后自动按顺序派审阅者，全部完成后自动让写作模型修订，这样不靠模型自觉。模型列表只有 1 个时跳过审阅。

## 4. #3 共享探路

- 新插件工具 `vibe_ask_scout({ question })`：把问题投给 #3，附上提问方的 #编号，排队执行。#3 的提示词要求把结论用 `send_agent_prompt` 回给提问的 tab，并在 #1 留摘要。
- 多个 tab 同时提问时按到达顺序处理，Paseo 投递本身会排队。

## 5. #4 执行

沿用第七轮第 7 条的任务看板，子代理必须认领子任务。后台命令与终端用 Paseo 终端工具开出，面板的「执行」一节列出 #4 的子代理、认领与开着的终端。#4 的提示词要求用完的终端自己关掉。

### 5.1 大型任务的资源准入

调度器同时监控本机和设置中登记的远程开发机。远程目标与显示名存 vibe_meta，默认不配置；默认每 60 秒通过非交互 SSH 读取 macOS/Linux 的可用内存、核心数和 1 分钟负载。远程采样与本地 15 秒采样独立，失败保留不可达原因并限频记录，不影响本地采样；远程最新状态存元数据，不混入本地 resource_sample 历史。

可用内存低于总量的 15% 或 1.5GB，或者 1 分钟负载超过核心数的 85%，判为紧张；本机另检查已提交内存超过 90%。阈值集中为常量。调度器主页与设置显示各主机资源、不可达与紧张状态。

vibe_resources 对任一任务 tab 及其子代理提供一行简报和紧张原因。执行开工提示附同一简报；#4、执行子代理与 #6 的角色提示要求在构建、全量测试、模拟器、打包前查询。任一主机紧张则排队，隔几分钟再查，已经运行的任务继续；该约束补充现有并发与文件冲突准入。

## 6. 任务之间互相感知

- 方案状态由任务阶段映射得来，不另存：

  | 方案状态    | 对应任务阶段          |
  | ----------- | --------------------- |
  | 草稿        | planning              |
  | 待确认      | awaiting_confirmation |
  | 执行中      | queued、executing     |
  | 复核/验证中 | reviewing、verifying  |
  | 待验收      | awaiting_acceptance   |
  | 已完成      | completed             |
  | 已放弃      | 已归档、failed        |

- 新插件工具 `vibe_project_plans`：列出同项目其它任务的方案状态、目标、涉及文件和最近更新时间，并标出与本任务方案文件重叠的条目。
- #2 写方案前、#4 开始执行前，提示词要求先调用它。有重叠就在方案里写明怎么避让，或排在哪个任务之后。
- 调度器已有的「文件范围重叠不并发」保持不变，作为硬约束兜底。
- 流程面板新增「同项目其它方案」一节。

## 9. WP-130 实现记录

没有改 `packages/`。

- **角色与编号**：tab 角色新增 `planner`（标签「方案」）；预建顺序 `FLOW_ROLE_ORDER` 为方案、探路、执行、复核、验证，不启用的可选角色跳过、编号顺延。`#1` 注入 `task.role.main`（群主），`#2` 注入 `task.role.planner` 加 `task.plan_format`。旧任务在活动阶段的任一回合发现缺角色 tab（`needsProvision`，按快照或当前默认判断）就补建，编号接在已有 tab 之后。旧任务的 `#1` 仍是创建时注入的规划规则，它输出的方案照旧保存。
- **模型列表**：`ModelDefaults.planners` 是有序 preset 列表；旧键 `planner`/`plan_reviewer` 由 core 迁移 19 改写为 `planners: [planner, plan_reviewer?]`，`cleanDefaults` 对读入的旧形状做同样转换（标 `COMPAT(planner-list)`）。只设了 `plan_reviewer`、没设 `planner` 的项目层无法表达成列表，迁移后沿用全局；但项目层显式 `plan_reviewer: null`（关闭审阅）迁移为只含全局 planner 的单元素列表，审阅保持关闭（全局也没有 planner 时只删旧键）。项目层列表整体覆盖全局列表；任务层 `planner` 选择只替换写作模型，`plan_reviewer: disabled` 关闭审阅。确认快照保持原形状（`planner` 为第 1 个，`plan_reviewer` 为第 2 个或 null）。
- **互审编排**（`vibe-board/server/tabs/plan-review.ts`）：`#2` 回合结束且有完整方案时，列表长度为 1 直接保存方案；否则开一个审阅周期，状态存 `task.control.planReview`（`planningControl` 保留此键），初稿和每条意见存 `plan_review` 沉淀（sourceKey `review:<cycle>:draft|<n>`）。审阅者是 `parent=#2` 的原生子代理，带 `vibe.plan_review` 标签，注入 `task.role.plan_reviewer`；按顺序一个接一个，每个拿到初稿和前面所有意见。启动失败或回合失败记为失败并跳过；全部失败时沿用初稿；否则把全部意见发给 `#2`，它的下一个方案即定稿，并在 `#2` 与 `#1` 追加「已定稿」状态。审阅期间初稿不保存为任务方案（阶段仍是规划）；审阅中 `#2` 又出新稿时周期不重开，后续审阅者读新稿。用户在审阅中 `/执行`（或在执行 tab 直接授权）会中止周期、停止审阅者并确认当前方案；`/停止任务` 同样中止。
- **只审一次**：一个确认轮次（`state.round` = 任务 `confirmedAt`）只自动审第一份完整方案；修订稿和之后的方案直接保存，面板标「修订稿（未再审阅）」，之后再改会提示可 `/重新审阅`。`/重新审阅` 是 RPC 命令（拒绝 agent 调用方），只接受主会话或方案 tab（面板按钮以 #1 身份发），对方案 tab 最新的完整方案开一个 `manual` 周期。
- **候选与失败**：审阅者带预设的全部模型（`candidates`/`attempt`）；启动失败、回合失败、无产出、超时、关闭、出错都换下一个候选，用户归档或回合被取消则直接记失败。失败的审阅者立即归档（create 成功但 send 失败的也归档），周期 done/cancelled 时归档其余审阅者。
- **恢复**：插件启动 5 秒后、之后每分钟、以及有审阅的任务每次回合事件，`recover` 扫描 reviewing/revising 周期：审阅者不存在、关闭、出错、空闲超过 60 秒没产出（有产出则补记意见）、超过超时（设置 `planReviewTimeoutMinutes`，默认 20）都按失败推进；revising 没有 `reviseSentAt` 就重发修订请求。`agent.closed` / `agent.archived` 事件同样按失败处理。所有写状态的地方在 await 之后重新读取最新状态再保存。
- **看板**：WP-127 的 `guardCreate` 只管父 tab 为执行 tab 的子代理，审阅者的父是 `#2`，直接放行；`agent.created` 的认领移交只看 `vibe.subtask` 标签，不受影响。
- **共享探路**：`vibe_ask_scout` 以提问方 agent 身份（`sourceAgentId`）把 `board.scout.ask` 发给最新的探路 tab，消息里写明提问方 #编号与 agentId；子代理提问时沿父链找到所属 tab。没有探路 tab、或探路已关闭时报错。
- **方案感知**：`vibe_project_plans` 与面板「同项目其它方案」共用 `coordination.projectPlans`。任务所属原生项目记在 `control.projectId`（`ensureTab` 写入，查不到时读一次 workspace 再写回），归档由 `workspace.archived` 记 `control.archivedAt`，因此归档后的任务仍能列为「已放弃」。状态按第 6 节由阶段映射，`paused` 不在表中，显示「已暂停」。最近更新时间来自 core 迁移 20 新增的 `task.updated_at`（任务命令每次写入时更新；迁移前的行在下一次改动前为空，回退 `confirmedAt`）。重叠用 `findOverlap` 比较本任务的文件（参数 `files`、审阅中的初稿或已存方案，含子任务 files）与对方方案文件；比较前把绝对路径按各自任务 worktree 根转成相对路径，转不了的列为「范围未知」，不参与重叠。进行中且重叠的排在最前；名称只给排序截断后的前 50 条并行读取，单个超过 1.5 秒就先显示 workspace id。项目判定失败 60 秒后重试。两个工具只接受任务 tab 或其子代理调用。

## 10. WP-131 实现记录

- **[core] `agent.user_prompt`**：用户来源的 `send_agent_message_request`（输入框、手机 outbox、CLI）和语音输入在投递前经过这个 before 钩子；带 `sourceAgentId` 的 agent 消息、插件会话（clientId `plugin:*`）发的消息、创建 agent 时的首条提示词不经过。没有插件注册这个钩子时宿主直接返回，不读 registry。请求只带 `agentId`、`workspaceId`、`messageId`、`text`、附件描述（类型、名称、mimeType，不含图片 base64）和 `sessionMode`。插件返回 `{ handled: true, note }` 时，宿主不启动回合，在该 agent 时间线记下这条用户消息（沿用 `messageId`）并追加 `note`，然后发事件 `agent.user_prompt_handled`，带原始图片和附件；第一个接管的插件结束调用链。宿主最多等这个钩子 5 秒，未返回、返回空、抛错或超时都照常投递。钩子放在 `messageReceipts` 的 send 里，手机重试同一 `messageId` 不会重复转发。
- **为什么转发要等 `agent.user_prompt_handled`**：钩子里只判断和入队，立即返回。插件只在收到宿主「已接管」的事件后才转发，所以钩子超时、宿主已经把消息交给 #1 时，插件不会再转一份，不会出现 #n 和 #1 都收到的重复。附件也随这个事件交给插件，钩子请求因此不必携带图片内容。事件 15 秒没到就放弃转发，并在 #1 写「转给 #n 失败：…，请重发」。
- **点名路由**（`vibe-board/server/tabs/group-chat.ts`）：只处理发给任务 anchor（#1）的消息。`@#n`（编号最多 3 位，后面的标点和空白去掉）以用户身份（不带 `sourceAgentId`）连同图片、附件 `send` 给 #n，#n 那边就是 `user_message`，第七轮的执行 tab 直接授权照常生效。随消息的 `sessionMode` 只在 #n 与 #1 是同一种 provider 时带上，否则在 #1 提示未生效。编号不存在、`@#n` 后没有内容时接管并提示；tab 已关闭、发送失败时在 #1 补一条失败行。不让 #1 的模型去转发，避免 agent 替用户授权。
- **「发给」**：选择存在插件内存（按 #1 agentId，3 分钟有效，插件重启回到群主）。转发真正成功才清除，失败保留以便重发。pill 写「将发给 #n 角色」；目标是执行 tab 时用红色盾牌图标并写「发送即授权执行」。客户端订阅 agent 列表，只对标题以 `#1 ` 开头的 agent 调 `vibe.task.group.targets` 核实；有选择时每 5 秒复查一次，跟上服务端的清除和过期。宿主插件 API 不能改输入框内容，所以前缀由服务端补。插件 RPC 经 WebSocket 调用时宿主不带 `callerAgentId`（只有 MCP agent 工具带），所以 RPC 区分不了用户客户端和在 shell 里自己连 daemon 的 agent；这与 agent 不带 `PASEO_AGENT_ID` 直接 `paseo send` 是同一条信任边界。
- **进展汇报**：`group.report(workspaceId, key, text, mode)` 写到 #1 的 `task-status` 行。`append`（默认）每条新增一行：回合结论、失败、中止、等审批、看板、审阅开始/全部完成/定稿/中止/送达失败/审阅者全部失败。`progress` 只用于插件自发的进度（审阅者 x/n 完成、阶段变化），在「上一条仍是同类进度行、仍是 #1 最后一条状态行、其间 #1 没有开始回合或收到用户消息」时原位替换。同 key 同文 30 秒去重；同 key 的 `append` 行 3 秒内连发时合并，窗口结束写最新一条。状态行只给用户看，不进入任何模型上下文，`get_agent_activity` 也不返回它们。
- **[core] tab 排序**：顶部 tab 原先按 agentId 排序批量加入（`addMissingEntityTabs` 对新出现的 agent 排序后追加），agentId 随机，所以任务 tab 乱序。新增标签 `paseo.tab-order`：带它的 agent 在每个 pane 里占着原有的位置按键值（数字按大小）重排，其它 tab 位置不变。插件在登记和刷新 tab 时把编号写进这个标签，旧任务在下次读取 tab（例如「发给」选择器加载）时补上。
