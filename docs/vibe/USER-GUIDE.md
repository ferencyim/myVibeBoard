# myVibeBoard 使用指南

myVibeBoard 在 Paseo 的原生 workspace 和 tab 里协作。一个任务对应一个独立 Git worktree workspace；规划、探路、执行、复核、验证各是一个普通 agent tab，标题为 `#编号 角色 · 模型`，编号从 1 递增、固定不复用。侧栏 workspace 列表就是任务列表。

第六轮改为编号 tab 与 tab 之间直接交流，不再有群聊容器。第七轮（WP-123）恢复一个轻量的「任务流程」面板：新建任务时一次预建全部流程 tab，用户可直接在任一 tab 对话，执行 tab 里的用户消息本身就是执行授权。本次发布的实测范围、截图和未测项以 WP-123 验收报告为准。构建、模型登录和连接分别见 [BUILD.md](BUILD.md)、[AGENTS-SETUP.md](AGENTS-SETUP.md)、[CONNECTIVITY.md](CONNECTIVITY.md)。

## 开始前

daemon 启用插件后，安装 `vibe-board`、`vibe-context`、`vibe-master`、`vibe-scheduler`、`vibe-maintain`、`vibe-stats`、`vibe-verify`。`vibe-board` 名称保留用于兼容插件身份，现在提供 tab 编号与清单、`/执行` `/通过` `/状态` `/重新审阅`、模型预设与 Agent 行为设置。插件应与本 fork 的宿主一起升级；不要只替换其中一个包。

先到「任务设置 → 管理项目与 Agent 预设」建立项目扩展，关联原生 Paseo 项目，核对主仓库路径和项目类型。证据验证需要这份配置；未关联会暂停并提示，不能靠模型猜建项目。

在同一管理页配置预设及各角色的默认模型：方案模型列表、探路、执行主代理、子代理、代码复核、验证。方案模型列表至少 1 个：第 1 个写方案，其余依次审阅，最后由第 1 个汇总修订（第八轮把原来单独的「规划」和「方案复核」合成了这个列表，旧设置自动迁移为「规划模型 + 方案复核模型（若启用）」）。项目设置了方案模型列表就整体覆盖全局列表，留空沿用全局。「Agent 行为」负责提示词与自动化设置。项目默认覆盖全局默认；确认方案时冻结当时的角色与模型快照，之后修改默认不会改写已确认任务。探路、代码复核可以不启用，方案、主代理、验证必须可用，子代理未选时沿用主代理。预设内模型按顺序失败接续，候选耗尽时显示原因，不会悄悄把任务当成成功。

## 把 qoder 接为 Paseo provider

qoder CLI 支持 ACP，可以按 `docs/custom-providers.md` 的 ACP 方式接入，不需要改宿主代码。在 `$PASEO_HOME/config.json`（默认 `~/.paseo/config.json`）的 `agents.providers` 下加入：

```json
{
  "agents": {
    "providers": {
      "qoder": {
        "extends": "acp",
        "label": "Qoder CLI",
        "command": ["qoderclicn", "--acp"]
      }
    }
  }
}
```

Windows 下可执行文件为 `qoderclicn.exe`，需要写绝对路径或在 PATH 中。先在 Paseo 之外用 `qoderclicn` 完成登录；凭据由 qoder 自己保存，不写进本仓库和 `config.json`。可用 `--config-dir <独立目录>` 指向隔离的登录与配置，便于测试时不碰默认 `~/.qoder-cn`。保存后重启 daemon，模型列表由 ACP 在连接时发现，默认模型为 DeepSeek-Flash，可在预设里按 provider 显示的模型名选择。ACP provider 默认通过 MCP 注入 Paseo 工具，`vibe_open_tab`、`get_agent_activity` 等才能使用；若某个 ACP 适配器无法在 `mcpServers` 非空时建会话，再按 `docs/custom-providers.md` 设置 `options.supportsMcpServers: false`，但那样会失去这些工具。

qoder 的权限模式由它自己的 ACP 模式提供。实测时建议在 provider 的 `command` 里加 `--permission-mode auto`，或在新建 tab 时选择自动放行模式；qoder 的 `auto` 仍可能拦截 `git commit` 等命令并等待确认，无人值守的端到端测试可用 `--permission-mode yolo`，日常使用则按需在 tab 里放行。否则验证 tab 运行测试、采集证据时可能停在权限审批上，任务会一直等待。模型 id 与显示名不同时（例如 `dfmodel` 显示为 `DeepSeek-Flash`），tab 标题使用 provider 模型目录里的可读名称，取不到才显示模型 id。

任何 provider 都可以担任任意角色，插件不再按角色强制只读或拒绝不支持的 provider；只读角色仅靠提示词约束。

## 新建任务并讨论方案

1. 在原生项目下新建 workspace，选择独立 worktree，在输入框写需求并附上参考文件或图片。首消息就是任务输入，不用另外填标题、描述、验收表单。插件把首个 agent 登记为 `#1 主会话`，并立即按项目/全局默认模型预建其它流程 tab：`#2 方案`、`#3 探路`、`#4 执行`、`#5 复核`、`#6 验证`。探路、复核默认为「不启用」时不建对应 tab，后面的编号顺延；预建 tab 不带初始 prompt，保持空闲，不消耗 token。
2. #1 是群主：理解你的意图，把需求转给 #2 方案、调查交给 #3 探路，跟进各 tab 并在 #1 汇总；它自己不写方案、不改代码。你也可以直接在 #2 里谈方案。#2 写方案前会用 `vibe_project_plans` 查看同项目其它任务的方案和涉及文件，有重叠就在方案里写明怎么避让或排在其后；任何 tab 都可以用 `vibe_ask_scout` 请 #3 探路调查，结论回到提问的 tab。
   方案模型列表有多个模型时，#2 出第一份完整方案后插件自动依次请其余模型审阅（审阅者是 #2 的子代理，不占顶部 tab，后审的能看到前面的意见），全部完成后插件请 #2 汇总修订，最终方案末尾附「审阅意见处理」。修订稿直接定稿，不再审阅，面板标为「修订稿（未再审阅）」。之后 #2 再改方案也不会自动审阅；要再审一轮，在 #1 或 #2 发送 `/重新审阅`，或点面板「方案审阅」一节的「重新审阅」按钮。审阅者用预设的第一个模型，启动或运行失败时依次换预设里的候选模型，候选用尽才跳过；单个审阅者超过超时（「Vibe 任务流程」设置页，默认 20 分钟）、被关闭或出错，同样按失败处理。插件重启后会检查进行中的审阅并接着推进。审阅进度与每条意见在任务流程面板「方案审阅」一节可见；定稿后 #1 收到一条状态。列表只有 1 个模型时跳过审阅。审阅中途你确认执行，会中止审阅并按 #2 当前的方案确认。
3. **#1 就是群聊**：在 #1 用 `@#编号` 开头（`＠＃４`、全角数字也行，编号最多 3 位，后面的标点和空格会去掉）发消息，这条消息以你的身份直接送到该 tab，#1 这一轮不运行，#1 里留一条「正在转给 #n」提示；附件和图片一起转过去。它的权威与你在该 tab 里直接说话相同，例如 `@#4 开始执行` 就是执行授权（照样过调度准入，审阅中会中止审阅）。**只要消息以 `@#n` 开头就会被转发**：想问 #1 关于 #n 的事，不要以 `@#n` 开头，例如写「#4 现在进展如何？」或「问一下 @#4 的情况」。编号不存在时不转发并提示可用编号；该 tab 已关闭或转发失败时，#1 会补一条「转给 #n 失败：原因，请重发」。`@#1` 或不加前缀照常交给 #1。#1 输入框上方的「发给」按钮可以选下一条消息的对象（群主或某个 tab），按钮上写着「将发给 #n 角色」；选的是执行 tab 时按钮带红色盾牌图标并写明「发送即授权执行」。消息真正送达后才回到群主，转发失败会保留选择方便重发；所选对象 3 分钟内有效。模式切换只作用于当前 tab：要改 #n 的模式，请到 #n 切换。各 tab 的进展以状态行出现在 #1：每轮结论摘要（「查看 #n」）、阶段变化、某 tab 等你审批（「请去 #n 处理」）、看板子任务认领与完成及越界告警、方案审阅开始/进度/定稿、失败与中止。回合结论、失败、中止和需要你处理的提示每条单独一行；只有审阅进度、阶段变化这类进度行会原位更新。同一类同样的内容 30 秒内只出现一次，短时间内连续的同类进展会合并成最新的一条。#1 自己的回合不汇报，状态行不触发模型，也不进入 #1 模型的上下文。
4. 方案仍使用固定的 `vibe-plan` JSON 段。不完整、仍在输出或没有验收条件的方案不能执行；普通的「认可」「确认」「可以」不构成执行授权。
5. 旧任务保持原编号：在继续对话或发送 `/执行` 时按当前默认补建缺少的角色 tab（例如第七轮的任务补一个 `#6 方案`），已有角色 tab 不重复创建。打开面板或 `/状态` 只读，不会新建 tab；暂停、完成、失败或归档中的任务也不补建。

方案、探路、方案审阅只靠提示词要求「不修改文件」，插件不再强制只读权限模式；这些角色以预设正常的权限运行，任何 provider 都可以担任。确认方案时冻结角色、模型、文件范围、子任务和验收条件。

## 执行、复核、验证与通过

用户在原生输入框发送 `/执行` 会保存当前 tab、#2 方案或 #1 中（按此顺序）最新的完整方案、确认时间和角色快照，并交给调度器。执行只能使用任务自己的附加 worktree。资源不足、文件范围冲突或前置子任务未完成时保留排队原因。确认时会把预建执行 tab 的实际模型冻结进本轮快照，之后修改默认不会改写已确认任务。

调度器准入后，插件把执行提示词发给**已存在的** `#4 执行` tab，而不是再开一个 tab。你也可以直接打开执行 tab 发消息：执行 tab 里的用户原生消息本身就是执行授权（等同确认），但仍要过调度准入。有完整方案时按该方案执行；还没有完整方案时，你这条消息本身就是任务说明，执行 agent 按它工作，状态和面板会注明「无方案，按用户在执行 tab 的指示执行」。插件在这条消息开始时补做调度准入和资源登记，通过后向执行 tab 发出执行确认；在此之前执行 agent 不会改文件。如果你只是提问，它会先回答、不改文件。准入不通过会在该 tab 提示原因并停止本轮；任务仍在排队时，调度器准入后插件会自动发出执行确认。执行中再发追问不会重复准入。agent 之间互发的消息不算授权。执行 tab 按方案使用原生 subagent 分工，子代理不占顶部 tab，计入并发限制。执行结束输出 `vibe-delivery` 完成标记后，插件照常进入代码复核（启用时）和验证，并在预建的 `#5 复核`、`#6 验证` tab 还没用过时复用它们；已经跑过一轮的复核/验证 tab 不再复用，改开新 tab，保证每轮独立。复核/验证同样是普通 tab，提示词要求不修改仓库文件，但不强制只读权限；验证 tab 需要能运行测试和采集证据。

验证 tab 会运行测试、启动采集器并写证据文件。如果 provider 把工具调用交给用户审批，验证会停在权限审批上，看起来像卡住；请到该 tab 放行，或给复核/验证角色的预设选择自动放行模式（如 accept edits / auto / bypass），避免整轮验证一直等待。验证期间人工批准的审批不会让结论作废，但验证 tab 自己修改仓库文件或 Git 状态会使本轮证据作废。

复核或验证发现问题时，任务会退回修复或暂停并记录原因。验证证据只对当前确认轮次和当前代码提交有效，不能沿用旧轮通过结论。结果摘要会追加到相关 tab 的时间线，不触发模型回合；任意任务 tab 发送 `/状态` 可显示阶段、各 tab 状态和最近结论。状态消息使用中文渲染，长文本可展开；每次 `/状态`、确认、准入结果、Git 结果都按时间顺序新增一行，相同内容 30 秒内不会重复追加；只有上下文看门狗提示固定一行原位更新。验证摘要使用可打开报告与证据的验证卡片。

验证完成后，输入 `/通过`，或在当前任务 tab 单独发送「通过」。这会尝试安全合并到项目本地 `main` 并 push `origin main`。每次通过尝试都会留下记录；重试要发起新的操作。出现未提交修改、主检出脏树、代码已变化或冲突时停止并说明原因，不会强制覆盖。已经合并而 push 失败时保留待推送状态，排除网络或权限问题后再尝试。完成后 workspace、worktree、tab 和沉淀都保留。

agent 之间用 `send_agent_prompt` 发送的消息以 agent 身份出现，不是用户授权；只有用户在原生输入框里的斜杠命令或消息能触发执行、通过或 Git 收尾。审批同理只能由用户处理：目标 tab 正在等审批或回答时，给它发消息会被拒绝并提示去该 tab 处理；任务 tab 与子代理调用 `respond_to_permission` 一律被拒绝。

方案范围发生变化时，先停止旧执行，再修改方案并重新确认。不要用换模型或重复执行绕过尚未停止的写者。

## 编号 tab 与接手者

每个任务 tab 的标题是 `#n 角色 · 模型`。编号由插件在 tab 创建时分配，任务内递增且永不复用；关掉 tab 后新开的 tab 继续使用下一个编号。手动点「+」新建的 tab 是普通会话，角色标为「会话」。

换模型就是开新 tab：点原生「+」、选择模型，说「继续 #3 的工作」。插件会为新 tab 编号，并注入同任务的 tab 清单与交流说明；新 agent 先用 `vibe_tabs` 和 `get_agent_activity` 读取 #3 的记录再接着做。子代理、归档 agent 不进入编号清单。

tab 之间直接使用现有 Paseo 工具：

- `vibe_tabs`：读取本任务每个 tab 的编号、agentId、角色、模型和状态；
- `list_agents` / `get_agent_activity`：查看同 workspace 的 agent 及其记录；
- `send_agent_prompt`：给另一个 tab 发消息；由 agent 发起时默认在对方完成后通知；
- `create_terminal` / `send_terminal_keys` / `capture_terminal` / `kill_terminal`：与没有 API 的命令行工具协作时开终端读写，用完关闭自己开的终端；
- `vibe_open_tab`：插件提供的开 tab 入口，可指定角色与任务说明；
- `create_agent`（`asTab: true`）：打开新的顶层 tab，可带 `vibe.tab.role` 标签。

本 fork 没有 `wait_for_agent`，等待完成使用 `send_agent_prompt` 的完成通知或 `get_agent_activity` / `get_agent_status` 轮询。

没有群聊容器或成员列表，但保留一个轻量的「任务流程」面板。它只在任务 workspace 显示内容，入口是 workspace 的「+」菜单里的「任务流程」，也可以从 Command Center 搜索「任务流程面板」打开；手机上是同一个菜单/sheet。面板显示当前阶段与阻塞原因、全部 tab（`#编号 角色 · 模型 · 状态`，点击切换到对应 tab）、可展开的各步结论（方案、探路、复核、验证、Git 结果），并提供「执行」「通过」「停止任务」「状态」按钮；「方案审阅」一节另有「重新审阅」按钮。按钮与斜杠命令走同一个服务端命令，仍然只认用户点击。tab 的关闭只影响展示，任务阶段、编号和历史记录保存在 vibe.db；需要核对时用 `/状态` 或 `vibe_tabs`。

每个任务 tab 创建时都会注入一段交流说明，写明自己的编号、角色、上下游位置、其它 tab 的编号与职责，以及何时用 `send_agent_prompt` 把结论交给谁、如何用 `vibe_tabs` / `get_agent_activity` 查看结果。这份清单只是 tab 创建时的快照，之后新开或关闭的 tab 以 `vibe_tabs` 的实时结果为准。

上下文到期前由 `vibe-context` 自动压缩，必要时按原模型冷启动接续；不再提供面板倒计时或手动压缩按钮。压缩与接续都保留公开会话历史，模型私有推理不会迁移。

## 手机与离线首消息

Android 在线使用原生 workspace 和 tab，斜杠命令与桌面一致。首消息 outbox 恢复为宿主的普通路径：插件不再接管 owner，断网时按宿主原生行为排队，恢复连接后创建 workspace 和首个 agent。

已有任务的后续消息、模型选择和提示词需要在线操作。旧手机看板副本、LWW 同步与旧积压不会导入。点到旧卡片通知时会显示「入口已停用」，请从项目的 workspace 进入新任务。

## 设置与自动维护

侧栏保留「Agent 行为」「自动维护」「总 agent」「调度器」等设置入口，不再有「Vibe Board」或「会话汇总」看板入口。自动维护先创建任务会话和方案，仍需你显式确认执行。Git 体检按分支/worktree 列出台账，并给出「建议合并 / 建议清理 / 需你决定 / 保留」的可直接确认方案（「需你决定」按原因分组，每组一句可批量拍板的建议），不再直接展示原始发现 JSON。总 agent 只排序派发已确认任务，并在完成后整理记忆与需求文档。维护规则、提示词和配置仍按一份配置选择多个项目，不为各项目复制规则。

### Agent 行为

「Agent 行为」页按插件分组列出当前注册的提示词，可直接编辑正文，也可只对某个项目覆盖；生效顺序为项目覆盖 > 全局覆盖 > 默认。占位符（如 `{{tabs}}`、`{{plan}}`、`{{summary}}`）和末尾的固定回复格式（`vibe-plan` 方案段、`vibe-delivery` 完成标记、维护方案的固定约束）只读，避免改坏解析。

第六轮精简后，一个场景对应一条模板：

| 插件          | 保留的提示词                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| vibe-shared   | `task.plan_format`（方案固定 JSON 段，只读后缀）                                                                                                                                                                                                                                                                                                                                                    |
| vibe-board    | `task.role.main`（#1 群主）、`task.role.planner`（#2 写方案）、`task.role.scout`（探路）、`task.role.plan_reviewer`（方案审阅者）、`board.plan_review.request` / `board.plan_review.revise`（审阅请求与修订请求）、`board.scout.ask`（探路请求）、`board.task.work`（执行主代理）、`task.role.subagent`（子任务）、`board.tabs.guide`（tab 交流说明）、`board.task.continuation`（`/接手 #n` 接续） |

## 从旧版本升级

**旧卡片不迁移。** 旧卡、旧群聊、旧提案、旧事件和手机积压不变成新任务。升级会先对本机 `vibe.db` 做一致性备份并只读检查；备份失败就中止删除。成功后删除旧卡片及附属表、无消费者的旧同步表，保留项目扩展、预设及候选顺序、默认模型、提示词覆盖、维护规则及计数、记忆、统计，以及新 task/artifact/证据。

旧任务代码须已在相应 worktree 中保存；不要把旧卡当作代码备份。升级前记录仍需继续的旧任务及 worktree 路径，升级后在那个任务的独立 worktree 中建立新会话、说明已有改动和剩余目标，重新规划确认。不要让新任务在项目主检出执行。

第六轮起会话内群聊容器与成员列表不再存在；任务数据新增 `tabs_json` 与下一个 tab 编号。第七轮起新建任务会预建全部流程 tab，旧任务在首次访问时按当前默认补建缺少的角色 tab；已确认的旧任务按当时的角色快照补建。旧任务的会话历史仍可查看，重新执行确认后照常走流程。

日用安装的复核者按以下顺序升级：

1. 结束或停止仍运行的任务，保存旧任务 worktree 中的改动，关闭桌面窗口并执行安装目录的 `stop-daemon.ps1`。
2. 在已复核的源码上构建服务端、App/桌面与插件依赖，运行 `scripts/vibe/install-local.ps1`。脚本只复制文件，不替你删除数据；默认目标为日用安装目录，仅由复核者明确运行。插件使用宿主提供的 SDK 运行，不需要保留源码 checkout 的 SDK 联接或复制 SDK 的 `dist/src`。
3. 按脚本输出安装或重载插件，启动新 daemon。首次打开共享数据库会自动先备份再迁移，不要手工提前 DROP 旧表。备份目录和迁移结果以启动日志为准。
4. 确认备份可读、项目配置等保留数据存在、侧栏没有旧入口，再新建一个任务走完验证和通过。手机也升级到对应新版。

首次升级时，多个插件可能在共享数据库迁移完成前各自备份一次，单份可能约百 MB。备份位于 `VIBE_HOME\backups\vibe-<时间>-<标识>.db`；默认日用安装对应 `<安装目录>\data\vibe\backups`。确认升级与保留数据正常后，可保留一份已校验的升级前备份，手动逐个删除其余指定 `.db` 文件（例如 `Remove-Item -LiteralPath '<完整备份文件路径>'`），不要递归删除备份目录。

安装使用 `robocopy /E`，源码删除过的旧看板文件会留在目标目录，不影响新版运行。每轮复制后脚本打印「目标目录中源码已不存在的文件」清单；它只列出普通文件，跳过目录联接/符号链接，不自动删除。按清单核对**同一已复核源码版本**的对应相对路径确已不存在，再手动逐个删除指定文件；不要删除整个插件目录、`node_modules` 或数据目录。旧版可能留下的文件包括 `<安装目录>\plugins\vibe-board\client\board\Board.tsx`、`client\detail\CardDetail.tsx`、`bin\vibe-board.mjs`（后两项也相对于 `plugins\vibe-board`）；实际可清理项以脚本清单和源码逐项核对为准。安装前已有的 SDK 普通文件副本也可能保留；无需为运行补回 SDK 源码。

新版读取旧布局，忽略不认识的布局字段，写回新增任务 tab 和关闭记录。降级到不认识任务会话的旧版时无法使用这些 tab；旧版可能忽略字段或丢弃其布局文件，所以升级前应保留 App 数据备份。数据库删除旧表后不要直接用旧插件启动，需由复核者决定从升级备份恢复的完整方案。
